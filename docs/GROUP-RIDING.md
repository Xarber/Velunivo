# Group rides and audio

Groups admit at most eight riders through a XXXX-XXXX invitation code. A separate admission peer and a full mesh of data channels carry profiles, locations, the exact navigation geometry and instructions. Neither battery nor Bluetooth credentials are shared. Recording groups share locations, while each recorder stores only its own GPS samples. Ending a ride or leaving the screen that owns its active ride leaves the group.

Leadership follows admission order. After a sixty-second absence the earliest reachable rider takes over; an original leader who reconnects with the same room identity regains leadership. An explicit departure relinquishes membership and priority. Leaders can remove riders; removed identities cannot rejoin the same room. Room identities expire after twelve hours and are not included in data backups. Codes are invitations rather than an identity verification system.

Voice is opt-in through Profile & Group Riding. Disabled voice never opens the microphone or starts the system call. If another connected participant has opted into voice, the roster shows an availability banner and an Enable voice chat action, which saves the preference and joins automatically. System End Call disables the saved preference without leaving the data group. A later Enable action is required to rejoin voice.

Microphone and incoming audio controls are independent. Muting the microphone stops capture tracks and replaces outgoing RTP sender tracks with null. Unmuting acquires a new audio-only stream. Muting all incoming audio retains individual rider mute choices. Video is optional and only negotiated between mutually consenting riders; audio-only participants never receive camera feeds.

## Native integration and limitations

`react-native-webrtc` 124.0.8 and its config plugin 15.0.2 require a new native build; Expo Go cannot provide this feature. The Android Expo module uses AndroidX Core Telecom 1.0.0 and an ongoing foreground call service. The existing iOS audio module adds an audio-only CallKit provider named Velunivo Group Ride. Navigation announcements preserve the active group audio session. Native end/mute events feed the common voice controller.

Native audio supports background execution, but operating-system suspension, termination, connectivity and signaling availability can interrupt the group. Presence and mesh dialing retry automatically, unhealthy audio connections restart ICE and rebuild, and foreground restoration explicitly resumes connections. Browser pages can be suspended in the background. No promise of uninterrupted background connectivity is made. Remote-network connectivity may require a configured TURN relay; STUN alone is not sufficient on every network.

## 1.0.9 — native transport and developer video

Native group rides, trip sharing and device sync now use react-native-webrtc directly, with native WebRTC registered before importing PeerJS. The previous hidden WKWebView/Android WebView transport is retired from those production paths. This removes hidden-page throttling and JSON injection/bridge serialization from connection setup. Foreground restoration resumes signaling and connections. Physical iPhone performance still needs verification; changing transport is not proof of hardware success.

All current clients use bounded string frames over PeerJS raw channels, avoiding the library's 16 KiB JSON-message limit and native Blob conversion. Reassembly is capped at 5 million characters per message, four incomplete messages per listener, and a twenty-second expiry. Admission waits for a route-received acknowledgement instead of closing the handshake channel after two seconds. This protects large GPX and profile packets from premature closure. Existing JSON/binary connections can still deliver decoded legacy objects; all participants should update for the new group/video behavior.

Joining a navigation group automatically selects the exact shared route and opens Explore, ready to start using the ordinary navigation controls. It never injects another rider's path into local recording. Navigation permissions and route warnings retain their normal behavior.

Profile & Group Riding → Video sharing is enabled by default; existing saved opt-out choices are retained. Sending and receiving require video sharing, map pins and voice enabled locally, plus the other rider's explicit video opt-in. Each group session starts with camera capture off. Each participant has a camera button alongside microphone mute. Camera off releases capture and detaches video RTP senders; backgrounding stops the camera, with automatic foreground restoration if still enabled. Voice and data stay independent of camera capture. The system group call remains an audio call; video is rendered only within map people pins.

Map people pins follow Life360's circular photo, white rim, app-accent outline and location tip, with initials when no photo is available. Camera-off participants fall back to their photo/initials. Video targets 96×96 at 6 fps and 80 kbps per recipient where encoder controls are supported. Capture dimensions/bitrate are negotiated constraints, not a guarantee on every physical camera. Small streams can still use noticeable data with seven recipients.

Validation includes real Chrome WebRTC with three peers: two opted into video and one audio-only, no video/camera request for the third, observed 96×96/6 fps capture, and stopped camera/null sender after disabling. A real PeerJS group test delivers a 10,000-point route and a ~39 KB profile. Native rendering/connection speed remains an on-device check. The updated hosted web build is required for matching client behavior; the PeerServer protocol and server package are unchanged.

Final 1.0.9 validation: 273 tests, lint and TypeScript checks pass. Full-app Chrome confirms automatic route adoption on joining. Availability changes bypass the routine presence throttle to avoid delaying media negotiation. Camera usage permission describes optional sharing explicitly. No local native compilation was performed.

## 1.0.10 — GPS visibility and idle microphones

Web GPS uses browser `enableHighAccuracy`, no cached fixes and a ten-second stationary refresh. Expo's native accuracy option alone was not being converted to the browser high-accuracy flag. A fresh approximate coordinate is displayable and shareable, while the existing 35-metre movement/guidance threshold remains unchanged. A coarse fix cannot advance recorded distance, trigger arrival or fabricate speed. Retry GPS appears for missing/stale locations rather than every approximate measurement. Permission denial still warns and ends navigation on acknowledgement.

Consenting group members publish their current location while planning as well as navigating. Map pins respect the global map-pins preference, but are independent of developer/video toggles. Photos/initials are always the baseline; an available mutually permitted camera feed replaces them. Native GPS callbacks also publish directly to the authoritative group connection, bypassing a visible React commit. Background location requires native background permission and the app's background navigation option. Suspension, force-quit and radio/network failure can still interrupt delivery; native WebRTC is not an exemption from operating-system limits.

Voice controllers begin with closed microphone capture. Established voice connections open capture only when manual mute is off. Losing the last connected voice peer closes tracks and detaches senders immediately; reconnection acquires fresh capture, respecting manual mute. Empty groups also release the native call audio session without disabling the saved voice preference. Camera capture likewise stops without connected media peers.

Validation: 277 automated tests, lint and TypeScript checks; Chrome full-app navigation with a 200-metre approximate fix still shows the other rider's initials pin with video off, without a spurious Retry GPS button. Real two-browser audio verifies no microphone request while alone and ended capture tracks after the last peer leaves. Native background delivery remains an on-device verification. No local native compilation.

### Media, shared activities and deep links (1.0.14, final revision)

The 1.0.13 physical-phone report identifies inconsistent one-way camera/audio. The following changes address concrete lifecycle/negotiation risks; they are not a claim that both installation containers have passed physical testing:

- Voice signals carry a connection session identifier. Old answers/candidates are rejected after replacement, native asynchronous remote-description/ICE operations are serialized, and late offers from disposed connections are suppressed. Optional IDs retain compatibility with older clients, but all riders should update for full stale-signal protection. No PeerServer change is required; deploy the updated web client.
- Sender replacement ignores peers removed during an asynchronous publication rather than tearing down healthy peers’ microphone/camera capture. Native audio activation/deactivation is serialized. Camera hardware captures at 160×120/30 fps; the negotiated pin encoder remains limited to 6 fps and 80 kbps, with browser capture remaining 96×96/6 fps. Hardware may choose its nearest supported resolution.
- CallKit reports the generic remote handle, caller name and supported capabilities. Mute changes propagate both ways. End/start/mute actions check their call UUID so a delayed old-call transaction cannot switch off a replacement call or change voice settings. Transient peer loss stops microphone capture but keeps the system call during recovery; removing the last peer ends it. A rejected CallKit transaction falls back to in-app audio instead of leaving WebRTC manually disabled. System call UI availability in LiveContainer/TrollStore still requires a phone test.
- `VelunivoSharedTrip` now uses the same native ActivityKit renderer as navigation/test activities, without relying on shared widget storage. The repeated postinstall patch also upgrades already-patched installations. The old renderer whitelist omitted this factory, explaining blank spectator activities.
- The installed iPhone 18 Pro simulator reproduces the shared-link problem: `velunivo:///settings` opens Settings, but both shared-link forms leave the app on the home tab. Expo NativeTabs excludes hidden routes. Main screens now live in the `(tabs)` group under a root Stack; shared screens live alongside that group, preserving public web paths and the four native tab buttons. Custom links normalize host and triple-slash forms.

Validation: regression tests cover stale connection messages, queued native-style SDP/ICE, transient-disconnect capture/call lifetime, renderer migration and tab-independent links. Real three-Chrome-peer WebRTC tests cover dynamic video opt-in, unchanged video DOM across 20 position updates, 96×96/6 fps browser capture, mutual video consent, mute/reacquisition, null senders after camera/microphone shutdown and no capture when alone. Full-app browser checks verify approximate location pins and automatic group route loading. Native changes require CI-built binaries; no local native compilation occurred. Incoming native pin video, lock-screen call controls, shared activity rendering and new deep links must be checked against that binary, not the installed 1.0.12 baseline.
