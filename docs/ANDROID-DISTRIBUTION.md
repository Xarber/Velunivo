# Android distribution readiness

Obtainium already works with the existing public GitHub APK releases; there is no separate Obtainium APK upload. README now includes its official import/redirect link, using `.github/obtainium.json`. Users can alternatively add `https://github.com/Xarber/Velunivo`, select `Velunivo.apk`, and let Obtainium track future releases. The reserved `1.0` AltSource release has no APK; binary releases remain `v*`.

The workflow has optional release-signing secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. The repository currently has none. Without them CNG uses development/debug signing; this is not a protected production identity. A maintained, backed-up private keystore is necessary for production updates. Changing certificates can require uninstalling old APKs (export data first) unless a supported signing-key rotation is deliberately planned. No certificate was silently changed or key generated by this update. Package versionCode must monotonically increase; normal CI currently uses run_number.

F-Droid is not an APK upload service. Its official repository reviews and builds public, freely licensed source. Preparation includes English/Italian store metadata and icons under `fastlane/metadata/android`, plus disabled draft metadata in `distribution/fdroid/app.velunivo.mobile.yml`. No F-Droid listing or merge request has been submitted, and no fake verified recipe is included.

Actual blockers found in installed dependencies:

- `expo-location/android/build.gradle`: Google `play-services-location:21.0.1`.
- `react-native-maps/android/build.gradle`: Google Maps, Base and Location services, even though Velunivo uses MapLibre on Android.
- A reproducible CNG/React Native source-build recipe, fixed source versionCode, dependency/license scan and appropriate F-Droid build environment remain necessary.

A FOSS Android flavor needs a genuinely functional non-GMS GPS/background implementation and exclusion of the unused Google Maps native module. Removing these libraries without replacing location would break navigation; scanner ignore rules are not a solution. After the flavor builds and navigation/background tests pass, use fdroidserver to validate metadata, then submit a merge request to `fdroid/fdroiddata` through an authenticated GitLab account. Store screenshots must be actual Android captures; iOS images have not been mislabeled as Android. Changelog files must match real built versionCode, so none were invented in advance. Existing Expo MIT notices remain intact.

## Android 17 capture targets (2.4.0)

The independent screenshot workflow now requests API 37 (Android 17), a Pixel 11 Pro hardware profile for phone captures, and a neutral 10-inch tablet profile at 2560×1600 for landscape tablet captures. Both run on CI with at least 4 GB emulator RAM; no Android SDK is downloaded to the developer's Mac. A missing Pixel 11 Pro profile must fail explicitly rather than relabel an older Pixel as a new model. Each capture manifest records the runtime API and hardware profile. Only verified native framebuffers may populate `fastlane/metadata/android/<locale>/images/phoneScreenshots` and `tenInchScreenshots`; raw log/proof images are not distribution screenshots.

Obtainium uses the GitHub release APK and does not accept a separate store screenshot upload. The repository's Fastlane/F-Droid metadata provides the requested phone/tablet image collection. Android 16 diagnostic images are provisional and must not be represented as Android 17 captures. The native welcome tour uses matching-platform images and a generic tablet shell; web images remain unframed responsive web previews.

Reference: https://developer.android.com/studio/releases/emulator — API 37 requires at least 4 GB of AVD memory.

Capture troubleshooting: the SDK repository names the Android 17 image `android-37.0`, not `android-37`. The workflow explicitly refreshes command-line tools (23.0 in the inspected repository) before checking hardware profiles; older preinstalled 16.0 tools only list phones through Pixel 8. Captures still assert runtime API 37 from the booted emulator itself.

The current SDK's bundled hardware list still lacks Pixel 11 Pro even after refreshing tools. CI therefore registers a display-only custom AVD profile using Google's published 6.3-inch, 1280×2856 screen, named explicitly “Pixel 11 Pro (display profile)”. This is an Android 17 emulator capture at the requested screen size, not physical Pixel hardware validation. The tablet remains an unbranded landscape 10-inch profile. The profile schema/data derives from AOSP's Apache-2.0 generic phone definition; source attribution is in the XML. No camera/back-of-device artwork or dated Pixel Tablet branding is used.

User-profile loading is explicitly scoped to a disposable CI `ANDROID_USER_HOME`; both SDK inventory and installation errors are retained as artifacts. Package installation retries only transient boot/service failures, never permanent `INSTALL_FAILED` errors. This prevents an early package-service startup race from looking like an incompatible APK.

Pixel profile validation uses the schema's `xxhdpi` density name (480 dpi) rather than the invalid literal `480dpi`. CI selects the explicit 23.0 tools directory, avoiding a pre-existing `latest` directory that caused SDK Manager to install refreshed tools into `latest-2` while the command path still selected older tools.

Android 17's initial tablet attempt booted but could not install the existing APK: PackageInstaller reported “Requested internal only, but not enough space”. The capture AVD now has an explicit 8 GB data partition rather than the old tablet profile's small default. This is CI storage only and does not consume the Mac's disk. Such permanent installation failures are logged without pointless retries.

Tools 23.0's compatibility wrapper delegates to the new Android CLI, whose package inventory uses slash-separated IDs rather than semicolons. Runtime preflight accepts both official formats. The custom Pixel 11 Pro display profile was positively listed by the refreshed toolchain after correcting the density schema.

After publication, the Android capture workflow runs separately from binary release publication. A complete verified Android 17 phone/tablet pair can refresh Fastlane phone/tablet metadata and native onboarding assets. Historical manual captures produce a downloadable metadata artifact but cannot replace previews for a different current source version. Both families must have matching observed app versions; portrait tablets, partial sets and older runtimes are rejected before any metadata changes. Screenshots remain absent from README and binary release assets. Commits generated by this workflow are conventional and unsigned.
