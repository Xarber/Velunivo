# X-Center ID summary sync

X-Center ID is the first item in Settings on web and mobile. The account screen discloses which summaries sync before sign-in. The two summary categories default to automatic sync after sign-in. Users can enable or pause each summary independently. Signing out ends the Velunivo session and preserves the private summaries in X-Center ID so they are available after signing back in. Velunivo provides no summary deletion action or summary DELETE endpoint. The web app refreshes approved summaries after opening, returning to the foreground, reconnecting, or changing a recorded ride. A second browser loads the existing account copy. It does not replace another browser’s revision automatically. After sign-in, enabled categories sync when data is available. Backup and direct device transfer remain available without an account. This does not import complete rides, settings or tracks into another device.

- Recent neighborhoods resolves up to eight recorded destinations from finished rides in the past 30 days. Photon receives approximate coordinates rounded to two decimal places after the user enables automatic sync for this category. The account receives only area names. These are approximate destination areas, not a complete list of places visited along a ride.
- Ride insights includes aggregate ride count, kilometers and minutes from finished rides in the past 30 days. Routes, timestamps, and vehicle identifiers are excluded.

## Trust boundaries and deployment

Register Velunivo as a confidential website with X-Center ID. The exact registered callback is `https://velunivo.xcenter.it/api/account/callback`. Confirm callback DNS ownership, activate the registration and enable its private app records. Configure `XCENTER_ID_CLIENT_ID` and `XCENTER_ID_CLIENT_SECRET` as server environment variables. Keep credentials out of Expo and browser builds. The server retains short-lived in-memory sessions and transactions. A restart requires signing in again.

The server pins the issuer, checks endpoint origins, validates the signed ID token with a stored nonce, checks state and PKCE, and checks UserInfo against the validated subject. Only the backend handles the opaque provider access token. The consent request includes profile, email and age range. The account panel displays the name or username, email and age range returned under their corresponding granted scopes. Writes require the production browser origin, a session binding and a matching record revision. The backend restricts collection names and payload fields and always writes private records without readers. Local sign-out clears the product session. Provider unlink/revocation is enforced by the records service on its next request. A separate issuer-mediated consent flow governs outgoing cross-app permissions.

Before activation, test real login, cancellation, replay, denied storage scope, unlink and expiry using an isolated account. Verify that a second account cannot read the first account's summaries and that conflicting updates reject stale revisions. Native sign-in opens a one-time HTTPS start URL at Velunivo in the system browser. The browser binds the transaction with a short-lived Secure HttpOnly cookie before redirecting to X-Center ID. The normal website callback performs the confidential OAuth exchange. It then displays a completion message with no session token or redemption code in the browser URL. The app checks for completion after returning to Settings. It proves possession of the verifier stored in SecureStore, and the backend allows a single redemption. Both the pending verifier and the resulting session use SecureStore. This flow works independently of Apple Universal Links, Android App Links and custom schemes.

Primary sources: [integration guide](https://id.xcenter.it/docs#manual) and the maintained AuthNJS identity and application-data implementations.

## App data categories

The X-Center ID screen offers Settings, Vehicles (including portable pictures and maintenance), Saved places, Saved routes, Recorded rides (including GPS tracks and recorded samples), and Exploration history. Each category has an independent switch and shows the estimated local UTF-8 payload size before compression. Categories of 256 KiB or more, recorded rides, and exploration history initially stay off. New sign-ins after the expanded disclosure enable smaller categories by default. Existing sessions retain their prior permission and can enable the new categories individually. All eight App data categories have their own rounded background. The two summary categories retain their independent sync switches and revision checks. Pausing a category stops future transfers on this device. Existing remote data remains in the account.

The category payload uses the existing portable backup schema and timestamp/record revision merge. Import overlays only the selected category onto the local envelope, then uses the ordinary validation and merge path. Default or disabled categories cannot remove unrelated records. Updates run on foregrounding, ride changes, reconnect on web, and every 90 seconds while in use. A ride lock defers portable sync during navigation or recording.

The backend stores compressed parts privately using X-Center ID's existing app data API. It switches the manifest with an expected revision after uploading every part. It cleans up the older generation after a successful switch. It avoids deleting the new generation when it cannot determine whether an interrupted request committed. The hard raw limit is 8 MiB per category, and the packed limit is 48 parts of 42,000 bytes. Account quota and upstream limits still apply. Peer transfer and file backup remain available for larger archives. Provider authentication and per-category session binding apply before parsing large requests. Pairing credentials, API keys, developer and simulation settings, memories media, and downloaded maps are excluded. Enabling rides exports location and sensor history to the private account store.

## Persistent sessions and account overview

The website backend discovers support for refresh tokens and offline access. When renewal is supported, each browser authorization requests offline access. The user controls **Stay signed in** on the X-Center ID consent page. If the issuer declines that scope or returns no refresh token, the product session expires with its access token. The account can still be used when storage permission is declined. Storage operations then stay disabled until the user grants app data access.

Velunivo gives browsers a secure HTTP-only product session cookie and keeps native product sessions in SecureStore. Users enter their sign-in credentials only on X-Center ID. When the active app needs an expiring token, the backend uses a single renewal per session. It removes the old durable token before attempting rotation and saves a replacement atomically. An uncertain response ends the product session and requires sign-in. Logout removes the product session, including an in-flight renewal. A successful renewal advances a 14-day idle deadline. The current deployment uses one web service process. A future replicated deployment needs a common session store and a distributed per-session refresh lock.

Production sets `XCENTER_ID_SESSION_DIR` to a service-owned state directory. In this directory authenticated AES-GCM envelopes are keyed to the product session and encrypted using a key derived from confidential per-app configuration. The state directory is private to the web service user. Issuer secrets are never bundled into clients. Native pickup can be canceled in the app. The server accepts cancellation only with the matching verifier and the pickup still expires on its own. Unsigned native builds continue to use the system browser and website callback.

The overview displays verified UserInfo name, username, permitted contact details, an authenticated photo, and the provider's verification and administrator indicators. The indicators never authorize app actions. The official mark is sourced from the X-Center ID Expo package (AGPL-3.0-only). Velunivo uses a local presentation based on the shared overview because its Expo 57 dependencies do not satisfy the package's Expo 58 peer requirements. **Manage X-Center ID** opens the provider profile. App sync controls remain separate from the identity card.

## Outgoing linked-app permissions

All eight sync categories appear in **App data**, including the two ride summaries. The settings rows render immediately after account status is known. Switch preferences are read separately from per-category size estimates. Estimates read local stored bytes and native photo file sizes without running an export, repairing old rides, or waiting for provider requests. The sync worker still enforces limits against the actual serialized payload.

Velunivo offers four collections for read-only cross-app consent. Save them in the Velunivo registration under **Developer → Manage app storage → Shared collections**. A verified destination registration must request the exact publisher client and collection. A user grants or revokes that request in X-Center ID. The authority is the issuer's user-specific grant. A sync switch controls updates to the account copy. To revoke a linked app's access, use **Manage app permissions**. Already imported destination copies are subject to the destination's retention policy.

| Collection | Record | Data |
| --- | --- | --- |
| `saved-places` | `current` | Schema 1 with the saved place ID, name, address, and longitude/latitude. |
| `exploration-history` | `current` | Schema 1 with visited tile count and de-duplicated resolution-7 H3 cells. No raw tracks, detailed tile IDs, or timestamps. |
| `recent-neighborhoods` | `summary` | The existing array of approximate neighborhood names. |
| `ride-insights` | `summary` | The existing 30-day aggregate ride count, distance in kilometers, and riding time in minutes. |

The first two projections are derived on the Velunivo server from the authenticated user's committed private archives. The two existing summary records already have the desired limited schema. All four collections use user-owned private records with no public flag or personal-reader ACL. Never offer any `velunivo-*` backup collection. The source session and account scope are checked before reading private archives or writing projections. Revision checks prevent competing publishers from replacing a newer projection. Provider record size applies to each projection. Larger projections report the sync size limit without changing the private backup.

Ensure the destination receives no data before consent, receives only the consenting user's records after consent, cannot write, and loses read access when the grant is revoked. Check anonymous collection listings separately. Installed iOS and Android should open the signed-in page without waiting for a large ride archive and present the persistence choice at the issuer.
