# Bluetooth vehicle bridge

## What is implemented and what is verified

Velunivo has one vehicle-independent, read-only BLE bridge. Vehicles → select vehicle → Add Bluetooth Pairing explains data use before Continue requests permissions. Discovery lists positive compatible advertisements only; connection verifies an identity and a telemetry response before saving a private app association. This is not a claim of operating-system Bluetooth bonding. Disconnect, reconnect, replace and forget are supported.

The initial production plugin implements legacy Xiaomi M365-family UART reads and the first-generation encrypted 5AA5 handshake used by compatible Pro 2 Bluetooth firmware. SHFW on the motor controller alone does **not** determine Bluetooth compatibility. Pro 2 BLE129 / compatible BLE132 are protocol targets, not hardware-certified combinations. Mi FE95 registration, saved-token login and authenticated 55AB telemetry are also implemented; see the physical validation below. Other manufacturers using FE95 are not implicitly supported. Do not change firmware to use this app. Authentication may ask for a power-button press; Velunivo never writes vehicle configuration, firmware, modes or limits.

**No physical scooter or e-bike communication was verified during this implementation.** Tests validate byte fixtures, encrypted authentication with an independent Node/OpenSSL fixture peer, state transitions, simulator behaviour and persistence. A fresh native GitHub build is needed for BLE; an older binary cannot gain the native module from JavaScript alone. Expo Go and the iOS Simulator do not provide the native production BLE transport. Web Bluetooth is implemented for capable browsers (Bluefy on iOS, Chrome/Edge on desktop/Android); Firefox and Safari do not expose it. Web also retains navigation/recording and the clearly labelled developer telemetry simulator. No genuine e-bike protocol is registered yet.

## Architecture and plugin contract

`src/bluetooth/types.ts` is the frontend contract. `service.ts` registers immutable plugins at build time; `registry.ts` filters by vehicle type and excludes simulator plugins from production discovery. No screen knows Xiaomi register addresses. The existing `escooter` / `ebike` profile kinds map to `electric_scooter` / `electric_bike`; the bridge also supports future bicycle/other protocols.

- `transport.ts`: lazy native BLE manager, advertisement decoding, permissions, bounded connection, notifications and 20-byte UART writes. `transport.web.ts` has no native imports and selects the browser GATT transport, with capability detection and explicit unsupported-browser guidance.
- `bridge.ts`: authoritative state, verified associations, shared connection, consumer leases, scan duration, retry backoff and partial telemetry publication.
- `telemetry.ts`: declared-field validation, SI units, per-field timestamps/source and freshness. Speed expires after 3 seconds, signal after 15 seconds, other readings after 30 seconds. A 2-second render-clock tolerance prevents fresh packets from flickering unavailable between UI ticks. Invalid units/ranges, undeclared fields and older timestamps cannot overwrite good readings.
- `persistence.ts`: SecureStore association index and per-vehicle records; ephemeral authentication challenges are never persisted. Web stores real verified associations in browser-local AsyncStorage; simulated sessions never become hardware associations. `preferences.ts` uses a separate versioned AsyncStorage key and does not replace existing app preferences.
- `react.tsx`: provider plus lightweight ride lease and telemetry subscriptions. Navigation and explicit recording consume the same singleton. Last ride consumer disconnects; manual disconnect stops retries. The retry delay grows from 1 second to 30 seconds. Foreground resume checks the existing target.
- `tripTelemetry.ts`: timestamped timeline samples and versioned summaries, independent of UI visibility.

A plugin declares `id`, manufacturer, supported vehicle types/models, advertised services, optional `manufacturerFilters` (company identifier and byte prefix), capabilities, authentication and compatibility limitations. `detect(device)` must return positive compatibility only with corroborating advertisement evidence or a completed browser protocol verification. An uncertain match is excluded. `open(link, context)` verifies the protocol and returns an immutable identity/capability session and an idempotent `close()`. `context.emit({fields, extensions})` publishes partial readings. `context.signal` cancels in-flight initialization when a connection is abandoned; plugins must clean up pending requests and subscriptions on abort. `context.phase()` supplies ordinary user-facing status; `context.random()` supplies cryptographically random bytes. Plugins never own application navigation or storage.

Readings contain `{value, timestamp, source, unit}`. Sources are `vehicle`, `calculated`, `gps`, or `simulator`; internal speed is m/s, distance/range m, voltage V, current A, power W, temperature °C, battery %, RSSI dBm. All fields are optional. Unsupported values stay absent. Manufacturer extension fields may retain ambiguous raw readings for diagnostics; do not promote them into a component-specific UI field without validated semantics. Add new plugins to `service.ts`, declare genuine capabilities, add detection/packet/error fixtures and a physical validation matrix. Do not register placeholders for future Ninebot or e-bike protocols.

## Initial Xiaomi wire contract

Native discovery matches manufacturer signatures `4e 42 20` / `4e 42 28` or `4e 43 00 20` / `4e 43 00 28`. UART may be absent from advertisements; the real GATT characteristics and read-only protocol are checked during connection. Vehicle names are user-editable and no longer gate discovery. Browser selections remain uncertain until the real protocol verifies serial and telemetry; generic UART alone is never a positive identity. A name alone or generic UART device is insufficient. This conservative advertisement contract may exclude otherwise compatible firmware; extend it only with validated advertisements and negative fixtures. Model labels remain “Xiaomi M365 family” until identity verification; no guessed exact Pro 2 model.

The write characteristic is UART `…0002…`, notifications `…0003…`. Plain packets are 55AA with a checked complemented additive checksum; the parser handles fragments/coalesced notifications. Only allowlisted read command `01` is sent, apart from required 5B/5C/5D encrypted session authentication messages. Reads are serial `10` (14 bytes), firmware `1A` (2 bytes, optional), ESC `B4` (16 bytes), ESC `B9` (2 bytes) and BMS `31` (10 bytes). Polling is sequential with a 350 ms minimum delay, not concurrent requests. Optional failed registers are disabled for that session; repeated primary-read failure disconnects for the bridge to reconnect.

ESC B4 provides battery %, speed in metres/hour (converted to m/s), and odometer metres. B9 provides trip metres. BMS31 provides percentage, signed current in centiamps, voltage in centivolts and legacy battery-temperature bytes offset by 20 °C. Calculated electrical power is labelled calculated and retains its sign; it is not an energy-consumption measurement. The frame-temperature register is retained only as an extension because references disagree about which component it represents. A negative current can represent regenerative braking; this plugin does **not** assert charging from current, and does not expose charging, mode, cycles, remaining range or controller/motor temperature as verified capabilities. Firmware variants and scaling need hardware confirmation.

`legacyCrypto.ts` independently implements the documented first-generation AES/SHA-1 wire format and key transitions with MIT-licensed noble primitives, authenticated checksums and replay rejection. The power-button approval challenge is ephemeral, reuses the same random app nonce during bounded retries and never changes scooter settings. Unsupported modern authentication fails visibly and leaves GPS navigation operational.

## Navigation, recording and settings

Real, connected speed replaces GPS speed only while fresh and visible; mapped road limit and configured riding/hardware limits remain separate. GPS remains the fallback after stale data/disconnection. `VehicleBatteryBadge` appears directly below the road-limit circle only for fresh actual battery readings. It uses normal colour at 40–100%, orange at 20–39%, red below 20%, accurate fill and a numeric percentage. It never substitutes 0 for missing data. A lightning icon requires a plugin's explicit, fresh charging field; the initial Xiaomi plugin cannot show one.

Settings → Bluetooth separates persistent per-capability display switches from **Collect trip telemetry**. Hiding a metric does not stop analytics collection. Disabling collection stops new BLE samples entering ride archives while GPS continues. Developer Mode exposes the simulator, labels every simulated reading, bypasses physical transport/permissions, and never saves an association or simulated battery/speed into real ride analytics.

BLE samples are attached at the existing GPS recording cadence, not every Bluetooth packet, and stored in existing 100-sample chunks. Each carries vehicle/plugin identity, connection state, readings and timestamps. The optional summary records start/end battery and interruptions. Existing records with no BLE data continue to load unchanged; additive optional fields require no destructive migration. New BLE preferences/associations and summary data each declare schema 1; unsupported association plugins/schemas are ignored, preferences fall back to defaults.

Automatic battery usage is saved only with a fresh connected real vehicle, an early start reading (first 15 seconds), an end reading within 30 seconds, at least 10 seconds between readings, no charging/battery increase, and no connection or battery-reading gap. It supplies the existing battery feedback system and learned range analytics without a second prompt. Otherwise the existing persistent **Ask for battery usage** preference decides whether the saved trip receives the existing skip-capable prompt. Missing/uncertain telemetry never blocks GPS recording. Charging or interrupted measurements do not become misleading subtraction-based battery usage. JSON includes the optional timeline/summary; GPX remains a location track, not a BLE archive.

## Native setup and background limits

Dependencies: `@sfourdrinier/react-native-ble-plx` 3.9.3 (maintained plx fork supporting RN0.86/Expo57), `expo-crypto` 57, `@noble/ciphers` 2.4 and `@noble/hashes` 2.4. BLE fork documentation: https://github.com/sfourdrinier/react-native-ble-plx . No firmware-modification dependency is included.

The existing Expo config plugin adds iOS Bluetooth permission text and central background mode, plus Android scan/connect/location permissions and its connected-device foreground service. Existing location background modes remain in place. iOS requires a development/release native build, Bluetooth permission, and compatible nearby hardware. Android 12+ requests Scan/Connect when Continue is pressed; older Android uses location permission for discovery. Android's scan is not marked neverForLocation because that can filter vehicle advertisements. The current Android session uses the library's foreground service while connected.

Background connectivity is best effort. iOS may defer notifications, throttle, suspend or terminate work; this implementation does not promise JS polling after app termination and does not claim CoreBluetooth restoration support. Returning to the foreground can reconnect an active consumer. Navigation/recording never depend on BLE availability. Simulator/background/permission behaviours still need native target testing.

Use the existing GitHub `release.yml` workflow for native builds; no local native compile, prebuild, Pods or SDK download was performed for this feature. Bluetooth permission metadata is extracted by the existing release/AltSource pipeline from the built application.

## 0.1.27 — Web Bluetooth / Bluefy

Open **https://velunivo.xcenter.it** in [Bluefy](https://bluefy.app/guide.html) on iPhone/iPad, or a Web Bluetooth-capable browser on Android/desktop. In Vehicles, open a personal scooter → Bluetooth → Continue. The browser chooser opens from that tap, before asynchronous work can lose user activation. Keep the browser open while navigating/recording. Safari, iOS browsers without a BLE bridge and Safari-installed home-screen PWAs remain unsupported; feature detection shows an explanation without requesting permissions. No native build or new package is needed for the web transport.

The shared bridge/plugin contract remains platform independent. `webTransport.ts` maps GATT service discovery, notifications, serialized 20-byte writes, connection loss and granted-device recall onto the existing BLELink. Notifications must be ready before sending a protocol request. Service/connect/write/notification setup have bounded timeouts. RSSI and advertisements are unavailable through ordinary browser GATT and are left missing, never invented. Older browser bridges can use `writeValue` when `writeValueWithoutResponse` is absent.

Web Bluetooth cannot provide the native app's passive filtered advertisement scan. The OS/browser chooser filters registered plugin service UUIDs, and may show other devices exposing the same UART service. **Velunivo's own compatible-device list only receives the selection after** a unique eligible plugin recognizes its candidate service, connects, verifies its real serial and reads valid telemetry. Failed/uncertain candidates are rejected without saving an association. Native advertisements still require corroborating manufacturer/service evidence; custom names are allowed. The browser verification marker only records the completed handshake; every association/reconnection still performs the normal real handshake again. No fake advertisement signature is synthesized. The initial plugin retains the documented M365 legacy/first-generation encrypted compatibility limitations; this does not add modern Mi firmware or real e-bike support.

Device IDs/associations are stored locally in the current browser. Reconnection uses the in-memory grant or optional `getDevices()` API and never opens a chooser automatically. If the browser cannot recall a grant after reload, use Replace device and Continue to explicitly select it again. Bluetooth state/RSSI are not reliably exposed, so adapter status is Unknown and failures are reported by connection attempts. Forgetting removes Velunivo's association; revoke the website's Bluetooth permission in the browser separately if desired.

Background/locked-screen support is browser dependent, particularly on iOS. Bluefy documents background peripheral controls, but continuous polling/background recording is not promised or verified. GPS navigation continues without telemetry. Native app background facilities remain unchanged.

## Native registration reliability (0.1.32)

Native BLE operations now wait for CoreBluetooth notification subscriptions to report `isNotifying` before sending registration packets. Android retains its existing subscription behavior; the library's Android flag does not reliably represent indications. Writes remain serialized in 20-byte chunks, choosing no-response only when the characteristic advertises it and otherwise using with-response. Each native write has a five-second deadline and a cancellable transaction. Disconnect cancels outstanding transactions. Notification setup and characteristic lookup are bounded too.

Mi authentication retains early notification errors, bounds individual writes and the overall handshake, reacts to cancellation, and limits random private-key generation attempts. Registration shows verification/confirmation phases rather than one opaque status. Radio/write failures are not converted into misleading headlight-approval retries. Tokens still become approved only after the scooter's registration acknowledgement, and live telemetry verification remains required for association.

Tests simulate notification readiness/failure, response-only characteristics, chunking, stalled native writes/cancellation, invalid randomness and aborted authentication. ## Charging status (2.5.0)
Read-only BMS register0x30 bit6 (`IsCharging`), documented in https://github.com/etransport/ninebot-docs/wiki/M365BMS, supplies positive charging proof. Negative current may be regenerative braking and is never used as charger proof. Unsupported/timeout registers retain existing poll backoff; do not fabricate a charging reading. This decoder needs charger-connected hardware validation. Bridge caches valid partial fields separately per vehicle and real/simulated source; missing/invalid updates retain the last valid reading with original timestamp. Forget removes cached readings.
